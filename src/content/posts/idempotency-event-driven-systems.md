<p>Imagine you’re building an order API.</p><p>A customer clicks Pay. Your server creates an order in PostgreSQL, but the HTTP response gets lost because of a network timeout.</p><p>The client retries.</p><p>Your server creates another order.</p><p>You now have two orders for one customer action.</p><p>The problem is that the client doesn’t know whether the original request failed or succeeded without delivering a response.</p><p>This is where idempotency comes in.Phase 1: Implement core idempotency with PostgreSQL</p><h3>Phase 1: Implement core idempotency with PostgreSQL</h3><p><strong>Goal: Prevent duplicate orders when clients retry requests.</strong></p><p>Let’s start with the simplest version of the problem.</p><p>A client sends:</p><pre>POST /v1/orders<br>Idempotency-Key: order_abc123<br>Content-Type: application/json</pre><pre>{<br>  &quot;amountCents&quot;: 100000,<br>  &quot;currency&quot;: &quot;INR&quot;<br>}</pre><p>The server should create the order once and return the same result when the client retries with the same key and payload.</p><h3>Step 1: Store the idempotency record</h3><p>We need to associate each key with the request and its eventual response.</p><p>Add these models to your Prisma schema:</p><pre>enum IdempotencyStatus {<br>  IN_PROGRESS<br>  COMPLETED<br>}<br><br>model IdempotencyRecord {<br>  id             String            @id @default(cuid())<br>  scope          String<br>  key            String<br>  requestHash    String<br>  status         IdempotencyStatus @default(IN_PROGRESS)<br>  responseStatus Int?<br>  responseBody   String?<br>  createdAt      DateTime          @default(now())<br>  updatedAt      DateTime          @updatedAt<br>  @@unique([scope, key], name: &quot;scope_key&quot;)<br>}<br><br>model Order {<br>  id          String   @id @default(cuid())<br>  userId      String<br>  amountCents Int<br>  currency    String<br>  createdAt   DateTime @default(now())<br>}</pre><p>The most important part is:</p><pre>@@unique([scope, key], name: &quot;scope_key&quot;)</pre><p>This tells PostgreSQL that a given idempotency key can only be claimed once within its scope.</p><p>The scope might represent a particular user and endpoint:</p><pre>const scope = `${userId}:POST:/v1/orders`;</pre><p>This prevents different users from colliding just because they happened to generate the same key.</p><h3>Step 2: Detect conflicting requests</h3><p>Suppose the original request contains:</p><pre>{<br>  &quot;amountCents&quot;: 100000,<br>  &quot;currency&quot;: &quot;INR&quot;<br>}</pre><p>But the client reuses the key with:</p><pre>{<br>  &quot;amountCents&quot;: 500000,<br>  &quot;currency&quot;: &quot;INR&quot;<br>}</pre><p>These are not retries of the same logical operation.</p><p>We need a request fingerprint so that we can detect the difference.</p><p>Install a stable JSON serializer:</p><pre>npm install express @prisma/client fast-json-stable-stringify</pre><p>Then calculate a hash:</p><pre>import { createHash } from &quot;node:crypto&quot;;<br>import stableStringify from &quot;fast-json-stable-stringify&quot;;<br><br>function hashRequest(input) {<br>  return createHash(&quot;sha256&quot;)<br>    .update(stableStringify(input))<br>    .digest(&quot;hex&quot;);<br>}</pre><p>The input should be validated and normalized before hashing. Include every field that changes the meaning of the operation.</p><p>If the same key is reused with a different hash, respond with 409 Conflict.</p><h3>Step 3: Implement the endpoint</h3><p>Assume authentication middleware sets req.user.id, and request validation has been performed as shown below.</p><pre>function sendExistingResponse(record, requestHash, res) {<br>  if (record.requestHash !== requestHash) {<br>    res.status(409).json({<br>      error: &quot;idempotency_key_reused&quot;,<br>      message: &quot;This key was used for a different request.&quot;,<br>    });<br>    return;<br>  }<br>  if (<br>    record.status !== &quot;COMPLETED&quot; ||<br>    record.responseStatus == null ||<br>    record.responseBody == null<br>  ) {<br>    res.status(409).set(&quot;Retry-After&quot;, &quot;1&quot;).json({<br>      error: &quot;request_in_progress&quot;,<br>    });<br>    return;<br>  }<br>  res<br>    .status(record.responseStatus)<br>    .type(&quot;application/json&quot;)<br>    .send(record.responseBody);<br>}<br><br>app.post(&quot;/v1/orders&quot;, async (req, res, next) =&gt; {<br>  const key = req.get(&quot;Idempotency-Key&quot;)?.trim();<br>  if (!key || key.length &gt; 200) {<br>    return res.status(400).json({<br>      error: &quot;invalid_idempotency_key&quot;,<br>    });<br>  }<br>  const userId = req.user.id;<br>  const { amountCents, currency } = req.body;<br>  if (<br>    !Number.isSafeInteger(amountCents) ||<br>    amountCents &lt;= 0 ||<br>    typeof currency !== &quot;string&quot; ||<br>    currency.toUpperCase() !== &quot;INR&quot;<br>  ) {<br>    return res.status(400).json({<br>      error: &quot;invalid_request&quot;,<br>    });<br>  }<br>  const input = {<br>    amountCents,<br>    currency: currency.toUpperCase(),<br>  };<br>  const scope = `${userId}:POST:/v1/orders`;<br>  const requestHash = createHash(&quot;sha256&quot;)<br>    .update(stableStringify(input))<br>    .digest(&quot;hex&quot;);<br>  const where = {<br>    scope_key: { scope, key },<br>  };<br>  try {<br>    // Fast path: replay an existing result.<br>    const existing = await prisma.idempotencyRecord.findUnique({<br>      where,<br>    });<br>    if (existing) {<br>      sendExistingResponse(existing, requestHash, res);<br>      return;<br>    }<br>    // Claim the key, create the order and persist its response<br>    // in one atomic PostgreSQL transaction.<br>    const result = await prisma.$transaction(async (tx) =&gt; {<br>      await tx.idempotencyRecord.create({<br>        data: {<br>          scope,<br>          key,<br>          requestHash,<br>          status: &quot;IN_PROGRESS&quot;,<br>        },<br>      });<br>      const order = await tx.order.create({<br>        data: {<br>          userId,<br>          amountCents: input.amountCents,<br>          currency: input.currency,<br>        },<br>      });<br>      const responseBody = JSON.stringify({<br>        id: order.id,<br>        amountCents: order.amountCents,<br>        currency: order.currency,<br>        status: &quot;created&quot;,<br>      });<br>      await tx.idempotencyRecord.update({<br>        where,<br>        data: {<br>          status: &quot;COMPLETED&quot;,<br>          responseStatus: 201,<br>          responseBody,<br>        },<br>      });<br>      return {<br>        status: 201,<br>        body: responseBody,<br>      };<br>    });<br>    return res<br>      .status(result.status)<br>      .type(&quot;application/json&quot;)<br>      .send(result.body);<br>  } catch (error) {<br>    if (error?.code === &quot;P2002&quot;) {<br>      // A concurrent request may have claimed this key first.<br>      // Resolve it by loading the winning record.<br>      try {<br>        const existing = await prisma.idempotencyRecord.findUnique({<br>          where,<br>        });<br>        if (existing) {<br>          sendExistingResponse(existing, requestHash, res);<br>          return;<br>        }<br>      } catch (lookupError) {<br>        return next(lookupError);<br>      }<br>    }<br>    return next(error);<br>  }<br>});</pre><h3>Why does this work?</h3><p>Three things are important.</p><p><strong>First, the database enforces uniqueness.</strong> Checking whether a key exists before inserting it is not enough. Two concurrent requests could both pass that check. The unique constraint closes this race.</p><p><strong>Second, we use one transaction.</strong> The idempotency record, order, and completed response are committed together. If the transaction fails, they all roll back.</p><p><strong>Third, we persist the original response.</strong> If the order is committed but the HTTP response is lost, the next request retrieves the stored response instead of creating another order.</p><p>In this design, the intermediate IN_PROGRESS state exists only inside the transaction. Other transactions generally won&#39;t see it before the completed record commits. This is intentional for a short-running database-only operation.</p><h3>Test the edge cases</h3><p>New key -&gt; Create an order</p><p>Same key and payload -&gt; Return the stored result</p><p>Same key, different payload -&gt; 409 Conflict</p><p>Two simultaneous requests with the same key -&gt; One order</p><p>Server crashes before transaction commit -&gt; Transaction rolls back</p><p>Server crashes after commit but before HTTP response -&gt; Retry replays the result</p><p>This is a good starting point for many APIs.</p><p><strong>At this stage, you do not need Redis or Kafka.</strong></p><p>However, this design assumes the work can be completed within a short database transaction. It becomes more complicated when an operation involves external services or long-running work.</p><h3>Phase 2: Add Redis only when there is a reason</h3><p><strong>Goal: Reduce duplicate work or improve coordination under contention.</strong></p><p>PostgreSQL already gives us durable idempotency. So why add Redis?</p><p>Redis can provide fast coordination or caching. For example, it can prevent multiple application instances from eagerly starting the same expensive workflow.</p><p>A simple lock can be acquired with SET NX:</p><pre>import { randomUUID, createHash } from &quot;node:crypto&quot;;<br><br>const RELEASE_LOCK = `<br>  if redis.call(&quot;GET&quot;, KEYS[1]) == ARGV[1] then<br>    return redis.call(&quot;DEL&quot;, KEYS[1])<br>  end<br>  return 0<br>`;<br><br>async function acquireLock(scope, key) {<br>  const lockId = createHash(&quot;sha256&quot;)<br>    .update(`${scope}:${key}`)<br>    .digest(&quot;hex&quot;);<br>  const lockKey = `idem-lock:${lockId}`;<br>  const token = randomUUID();<br>  const acquired = await redis.set(lockKey, token, {<br>    NX: true,<br>    PX: 30_000,<br>  });<br>  if (acquired !== &quot;OK&quot;) {<br>    return null;<br>  }<br>  return { lockKey, token };<br>}<br><br>async function releaseLock(lock) {<br>  if (!lock) return;<br>  await redis.eval(RELEASE_LOCK, {<br>    keys: [lock.lockKey],<br>    arguments: [lock.token],<br>  });<br>}</pre><p>Here, redis is an initialized node-redis client.</p><p>The random token ensures that a worker releases only the lock it acquired. Otherwise, an expired lock could be acquired by another worker, and the original worker could accidentally delete the new worker’s lock.</p><p>There is an important limitation: the lock expires after 30 seconds. The original operation could still be running when that happens.</p><p>Therefore:</p><ul><li>Keep PostgreSQL’s unique constraint.</li><li>Keep the database transaction as the correctness boundary.</li><li>Treat Redis as a coordination optimization.</li><li>Have a clear policy when a lock cannot be acquired.</li></ul><p>For most early-stage applications, skip Redis until measurement shows that it solves a real problem.</p><h3>Phase 3: Introduce Kafka when asynchronous processing is needed</h3><p><strong>Goal: Let other services react to an order without making the HTTP request wait for all of them.</strong></p><p>Suppose an order now needs to trigger:</p><ul><li>Fulfillment.</li><li>Email notifications.</li><li>Analytics.</li><li>Inventory updates.</li></ul><p>One option is to call every service directly after creating the order. But that makes the request slower and couples order creation to downstream availability.</p><p>Kafka lets the order service publish an event such as:</p><pre>{<br>  &quot;eventId&quot;: &quot;evt_123&quot;,<br>  &quot;type&quot;: &quot;order.created&quot;,<br>  &quot;payload&quot;: {<br>    &quot;orderId&quot;: &quot;ord_123&quot;,<br>    &quot;userId&quot;: &quot;usr_456&quot;<br>  }<br>}</pre><p>Other services can consume the event independently.</p><p>A KafkaJS producer can look like this:</p><pre>import { Kafka } from &quot;kafkajs&quot;;<br><br>const kafka = new Kafka({<br>  clientId: &quot;order-service&quot;,<br>  brokers: process.env.KAFKA_BROKERS.split(&quot;,&quot;),<br>});<br><br>const producer = kafka.producer({<br>  idempotent: true,<br>  maxInFlightRequests: 1,<br>});<br><br>await producer.connect();</pre><h3>But we now have a new problem</h3><p>What if the order is saved in PostgreSQL, but Kafka is unavailable?</p><p>Or what if Kafka receives the event, but the database transaction later rolls back?</p><p>PostgreSQL and Kafka are two independent systems. A normal PostgreSQL transaction cannot atomically commit writes to both.</p><p>This is called the <strong>dual-write problem</strong>.</p><p>Adding Kafka gives us asynchronous communication, but it also creates a reliability requirement: when an order commits, we must reliably remember to publish its event.</p><p>That’s the motivation for the next phase.</p><h3>Phase 4: Add the transactional outbox</h3><p><strong>Goal: Ensure a committed database change and the intention to publish its event are recorded together.</strong></p><p>The outbox pattern is simpler than it sounds.</p><p>Instead of trying to save the order and publish to Kafka as unrelated steps, insert an event record into PostgreSQL during the same transaction as the order.</p><p>Add this model:</p><pre>model OutboxEvent {<br>  id          String   @id @default(cuid())<br>  type        String<br>  aggregateId String<br>  payload     Json<br>  attempts    Int      @default(0)<br>  claimedAt   DateTime?<br>  claimToken  String?<br>  publishedAt DateTime?<br>  createdAt   DateTime @default(now())<br>  @@index([publishedAt, claimedAt, createdAt])<br>}</pre><p>Extend the transaction from Phase 1:</p><pre>const result = await prisma.$transaction(async (tx) =&gt; {<br>  await tx.idempotencyRecord.create({<br>    data: {<br>      scope,<br>      key,<br>      requestHash,<br>      status: &quot;IN_PROGRESS&quot;,<br>    },<br>  });<br>  const order = await tx.order.create({<br>    data: {<br>      userId,<br>      amountCents: input.amountCents,<br>      currency: input.currency,<br>    },<br>  });<br>  await tx.outboxEvent.create({<br>    data: {<br>      type: &quot;order.created&quot;,<br>      aggregateId: order.id,<br>      payload: {<br>        orderId: order.id,<br>        userId,<br>        amountCents: order.amountCents,<br>        currency: order.currency,<br>      },<br>    },<br>  });<br>  const responseBody = JSON.stringify({<br>    id: order.id,<br>    amountCents: order.amountCents,<br>    currency: order.currency,<br>    status: &quot;created&quot;,<br>  });<br>  await tx.idempotencyRecord.update({<br>    where: {<br>      scope_key: { scope, key },<br>    },<br>    data: {<br>      status: &quot;COMPLETED&quot;,<br>      responseStatus: 201,<br>      responseBody,<br>    },<br>  });<br>  return { status: 201, body: responseBody };<br>});</pre><p>We now commit three things atomically:</p><ol><li>The order.</li><li>The completed idempotency response.</li><li>The outbox event.</li></ol><p>If the transaction fails, all three roll back.</p><p>If it succeeds, the outbox event remains in PostgreSQL even if Kafka is unavailable.</p><p><strong>The API no longer needs to wait for Kafka. A separate worker can publish the event later.</strong></p><h3>Build the outbox dispatcher</h3><p>A background worker claims unpublished events, sends them to Kafka, and marks them as published.</p><p>Multiple workers must not freely claim the same rows at the same time. PostgreSQL’s FOR UPDATE SKIP LOCKED can help coordinate claims.</p><p>For example, a dispatcher can claim a batch in a short transaction:</p><pre>import { randomUUID } from &quot;node:crypto&quot;;<br><br>async function claimOutboxBatch(limit = 100) {<br>  const token = randomUUID();<br>  const events = await prisma.$transaction((tx) =&gt;<br>    tx.$queryRaw`<br>      WITH candidates AS (<br>        SELECT &quot;id&quot;<br>        FROM &quot;OutboxEvent&quot;<br>        WHERE &quot;publishedAt&quot; IS NULL<br>          AND (<br>            &quot;claimedAt&quot; IS NULL<br>            OR &quot;claimedAt&quot; &lt; NOW() - INTERVAL &#39;1 minute&#39;<br>          )<br>        ORDER BY &quot;createdAt&quot;<br>        LIMIT ${limit}<br>        FOR UPDATE SKIP LOCKED<br>      )<br>      UPDATE &quot;OutboxEvent&quot; AS e<br>      SET<br>        &quot;claimedAt&quot; = NOW(),<br>        &quot;claimToken&quot; = ${token},<br>        &quot;attempts&quot; = e.&quot;attempts&quot; + 1<br>      FROM candidates<br>      WHERE e.&quot;id&quot; = candidates.&quot;id&quot;<br>      RETURNING<br>        e.&quot;id&quot;,<br>        e.&quot;type&quot;,<br>        e.&quot;aggregateId&quot;,<br>        e.&quot;payload&quot;<br>    `<br>  );<br>  return { token, events };<br>}</pre><p>After claiming the batch, publish each event:</p><pre>async function dispatchOutboxBatch() {<br>  const { token, events } = await claimOutboxBatch();<br>  for (const event of events) {<br>    try {<br>      await producer.send({<br>        topic: &quot;orders&quot;,<br>        acks: -1,<br>        messages: [{<br>          key: event.aggregateId,<br>          value: JSON.stringify({<br>            eventId: event.id,<br>            type: event.type,<br>            payload: event.payload,<br>          }),<br>        }],<br>      });<br>      await prisma.outboxEvent.updateMany({<br>        where: {<br>          id: event.id,<br>          claimToken: token,<br>        },<br>        data: {<br>          publishedAt: new Date(),<br>          claimedAt: null,<br>          claimToken: null,<br>        },<br>      });<br>    } catch (error) {<br>      // Keep the event unpublished so a later attempt can retry.<br>      console.error(&quot;Outbox publication failed&quot;, {<br>        eventId: event.id,<br>        error,<br>      });<br>    }<br>  }<br>}</pre><p>The one-minute lease is illustrative. Production implementations need bounded retries, backoff, monitoring, and lease management appropriate to the workload.</p><h3>One more edge case</h3><p>Imagine:</p><ol><li>The worker publishes the event successfully.</li><li>Kafka acknowledges it.</li><li>The worker crashes before setting publishedAt.</li></ol><p>The worker eventually retries the event, so Kafka may receive it twice.</p><p>This is expected.</p><p>The outbox prevents the intent to publish from being lost when the database transaction commits. It does <strong>not</strong> guarantee that each event is published only once.</p><p>For that, we need one more safeguard.</p><h3>Phase 5: Make Kafka consumers idempotent</h3><p><strong>Goal: Prevent repeated event delivery from repeating business effects.</strong></p><p>Suppose the fulfillment service receives order.created and creates a fulfillment job.</p><p>If Kafka delivers the event twice, the service must not create two jobs.</p><p>Add two models:</p><pre>model ProcessedEvent {<br>  eventId     String   @id<br>  processedAt DateTime @default(now())<br>}<br><br>model FulfillmentJob {<br>  id        String   @id @default(cuid())<br>  orderId   String   @unique<br>  createdAt DateTime @default(now())<br>}</pre><p>Now process the event in a transaction:</p><pre>async function handleOrderCreated(event) {<br>  try {<br>    await prisma.$transaction(async (tx) =&gt; {<br>      // Claim this event exactly once in our database.<br>      await tx.processedEvent.create({<br>        data: {<br>          eventId: event.eventId,<br>        },<br>      });<br>      // Apply the corresponding business effect.<br>      await tx.fulfillmentJob.create({<br>        data: {<br>          orderId: event.payload.orderId,<br>        },<br>      });<br>    });<br>  } catch (error) {<br>    if (error?.code === &quot;P2002&quot;) {<br>      const previous = await prisma.processedEvent.findUnique({<br>        where: {<br>          eventId: event.eventId,<br>        },<br>      });<br>      if (previous) {<br>        return; // Already applied successfully.<br>      }<br>    }<br>   throw error;<br>  }<br>}</pre><p>The event marker and fulfillment job commit together.</p><p>If fulfillment creation fails, the processed-event marker rolls back too. If the handler succeeds but the consumer crashes before its Kafka offset is committed, Kafka may redeliver the event. The processed-event table prevents that delivery from repeating the database effect.</p><p>This example assumes duplicate deliveries retain the same stable eventId and that the business effect occurs in the same database. External side effects, such as sending an email or calling another service, need their own reliability strategy.</p><h3>Phase 6: Know when to stop adding complexity</h3><p>Basic API with ordinary CRUD -&gt; PostgreSQL and Prisma</p><p>Safe retries for order creation -&gt; PostgreSQL idempotency records and a transaction</p><p>Faster coordination under high contention -&gt; Consider Redis</p><p>Multiple services need asynchronous events -&gt; Consider Kafka</p><p>Events must reliably follow committed database changes -&gt; Add an outbox</p><p>Duplicate event delivery must not repeat business effects -&gt; Idempotent consumers</p><p>One special case deserves extra care: payments.</p><p>If an external payment provider successfully charges a customer but your service times out before receiving the response, a local PostgreSQL transaction cannot undo that charge. Use provider-side idempotency keys where supported, persist operation state, and reconcile uncertain outcomes instead of blindly retrying.</p><h3>Final thoughts</h3><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*jrFe0y9ecP6inLhIQK3DfA.png" /></figure><p>Idempotency isn’t about adding as many reliability tools as possible.</p><p>It’s about identifying failure modes and choosing the simplest architecture that handles them.</p><p>PostgreSQL protects the core database operation. Redis can improve coordination. Kafka enables asynchronous communication. The outbox records the intention to publish an event alongside the business change. Idempotent consumers protect downstream business effects.</p><p>Each layer should exist because there’s a requirement it satisfies.</p><p>Start simple. Introduce complexity when the system gives you a reason to.</p><p><strong>Good system design isn’t about using every tool. It’s about understanding which guarantee you need, where that guarantee comes from, and what can still fail.</strong></p><h3>Further reading</h3><ul><li><a href="https://www.prisma.io/docs/orm/prisma-client/queries/transactions">Prisma transactions</a></li><li><a href="https://www.prisma.io/docs/orm/prisma-client/special-fields-and-types/working-with-composite-ids-and-constraints">Prisma compound IDs and constraints</a></li><li><a href="https://redis.io/docs/latest/commands/set/">Redis SET command</a></li><li><a href="https://kafka.js.org/docs/producing">KafkaJS producing messages</a></li></ul>
